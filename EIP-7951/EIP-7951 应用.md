# EIP-7951

为什么以太坊要支持 EIP-7951

我们日常使用的手机和电脑中，其实内置了专门的安全芯片。比如 iPhone 里的「安全隔区」（Secure Enclave），或者安卓手机里的 Keystore / Trust Zone / StrongBox。这块独立的物理区域通常被称为 TEE（可信执行环境）。它的特点是「只进不出」：私钥在里面生成，永远不会离开这个物理区域，外部只能请求它对数据进行签名。

这实际上就是硬件钱包的标准。而这些芯片在签名时，普遍采用了一种被 NIST（美国国家标准与技术研究院）选中的行业标准算法曲线：secp256r1。这也正是 WebAuthn 和 FIDO2（比如你的指纹登录、FaceID）背后的基石。

尴尬的是，以太坊原生并不支持这个主流的 secp256r1。当年比特币社区出于对 NIST 曲线可能存在「国家级后门」的担忧，选择了相对冷门的 secp256k1，所以以太坊在设计账户体系时，沿用了这条曲线的传统。虽然 r1 和 k1 看起来只差一个字母，但在数学上它们完全是两种不同的语言。这就导致了一个巨大的痛点：你手机里那个安全芯片，对着以太坊是一脸懵逼的，它无法直接签署以太坊的交易。以太坊显然无法强迫苹果或三星去更改芯片设计来适配 secp256k1，唯一的路就是以太坊自己去适配 secp256r1。

用智能合约写代码去验证 r1 签名行不行？理论上行，但数学运算太复杂，跑一次验证可能要消耗几十万 Gas，这在经济上是完全不可用的。

于是，在 Fusaka 升级中，开发者祭出了大杀器：预编译合约（Precompile）。 这相当于在以太坊虚拟机（EVM）里开了一个「后门」或「外挂」。与其让 EVM 一步步算，不如把这个验证功能直接写进客户端底层代码里。开发者只需要调用特定的地址，就能以极低的成本完成验证。

**EIP-7951 原生支持 secp256r1 (P-256) 签名算法**，这意味着：

✅ **钱包可以直接调用 iPhone/Android 的安全芯片**  
✅ **支持 Passkeys（通行密钥）和 WebAuthn**  
✅ **告别助记词**：不再需要备份 12/24 个单词  
✅ **生物识别登录**：Face ID、Touch ID、指纹识别成为链上交互的原生标准  

## 重要澄清：secp256r1 的使用范围

### ❌ 传统 EOA 交易不支持 secp256r1

**以太坊的传统系统交易（EOA 发起的交易）仍然只能使用 secp256k1**：

```
传统 EOA 交易流程：
用户 EOA 账户
  ↓ 使用 secp256k1 签名
协议层验证（只支持 secp256k1）
  ↓
交易执行
```

**原因**：
- 以太坊协议层的交易验证硬编码了 secp256k1
- EIP-7951 只是添加了预编译合约，**只能在智能合约中调用**
- 预编译不能改变协议层的交易验证逻辑

### ✅ 任何智能合约都可以使用 secp256r1

**EIP-7951 是一个预编译合约（地址 `0x100`），任何智能合约都可以调用它来验证 secp256r1 签名**。

#### 通用使用方式

**任何智能合约都可以直接调用 EIP-7951 预编译**：

```solidity
contract AnyContract {
    // 预编译地址
    address constant P256_VERIFY = address(0x100);
    
    function verifySecp256r1Signature(
        bytes32 messageHash,
        uint256 r,
        uint256 s,
        uint256 publicKeyX,
        uint256 publicKeyY
    ) public view returns (bool) {
        // 构建输入（160 字节）
        bytes memory input = abi.encodePacked(
            messageHash,  // 32 bytes
            r,            // 32 bytes
            s,            // 32 bytes
            publicKeyX,   // 32 bytes
            publicKeyY    // 32 bytes
        );
        
        // 调用预编译验证签名
        (bool success, bytes memory result) = P256_VERIFY.staticcall(input);
        require(success && result.length == 32, "Verification failed");
        
        // 检查结果：0x0000...0001 表示验证成功
        uint256 verified = abi.decode(result, (uint256));
        return verified == 1;
    }
}
```

#### 常见应用场景

**1. ERC-4337 智能合约钱包**（最常用）
```
用户操作 → 使用 secp256r1 签名 → 钱包的 validateUserOp → 调用 EIP-7951 预编译验证
```

**2. EIP-7702 + ERC-4337**
```
EOA 临时设置代码 → 使用 secp256r1 签名 → 调用 EIP-7951 预编译验证
```

**3. 其他智能合约应用**
- 多签钱包：验证多个 secp256r1 签名
- 权限管理：使用硬件签名进行权限验证
- 游戏应用：验证玩家设备签名
- DeFi 应用：自定义签名验证逻辑

### 🔮 未来可能：EOA 交易支持 secp256r1

有一些提案（如 EIP-7932 + EIP-8030）试图让 EOA 交易也支持 secp256r1，但这些还在**草案阶段**，需要：
- 协议层修改
- 新的交易类型
- 额外的 Gas 成本

**当前状态**：
- ❌ EOA 交易：只能使用 secp256k1
- ✅ 智能合约钱包：可以使用 secp256r1（通过 EIP-7951）



## 为什么这是革命性的？

### 传统方式（secp256k1）

```
用户创建钱包
  ↓
生成助记词（12/24 个单词）
  ↓
用户必须安全保存助记词
  ↓
每次交易需要：
  - 输入密码解锁钱包
  - 或者使用硬件钱包
  ↓
用户体验：复杂、容易丢失、门槛高
```

### EIP-7951 方式（secp256r1）

```
用户创建钱包
  ↓
使用设备安全芯片（Apple Secure Enclave / Android Keystore）
  ↓
密钥存储在硬件安全模块中（无法导出）
  ↓
每次交易：
  - Face ID / Touch ID / 指纹识别
  - 自动签名
  ↓
用户体验：简单、安全、原生
```

## EIP-7951 如何实现？

### 1. 协议层预编译支持

EIP-7951 在以太坊协议层添加了 `P256VERIFY` 预编译合约（地址 `0x100`），可以直接验证 secp256r1 签名：

```solidity
// 预编译地址
address constant P256_VERIFY = address(0x100);

// 验证签名（160 字节输入）
bytes memory input = abi.encodePacked(
    messageHash,  // 32 bytes
    r,            // 32 bytes  
    s,            // 32 bytes
    qx,           // 32 bytes (公钥 x 坐标)
    qy            // 32 bytes (公钥 y 坐标)
);

(bool success, bytes memory result) = P256_VERIFY.staticcall(input);
// 成功返回 0x0000...0001，失败返回空
```

### 2. 硬件安全模块支持

现代移动设备的安全芯片都使用 secp256r1：

| 设备/平台 | 安全芯片 | 签名算法 |
|----------|---------|---------|
| iPhone | Apple Secure Enclave | secp256r1 |
| Android | Android Keystore | secp256r1 |
| FIDO2/WebAuthn | 各种硬件密钥 | secp256r1 |
| Windows Hello | TPM | secp256r1 |

**关键优势**：
- 密钥存储在硬件安全模块中，**无法导出**
- 签名在安全芯片内部完成，**私钥永不离开设备**
- 支持生物识别解锁，**用户体验无缝**

### 3. EIP-7951 对 ERC-4337 和 EIP-7702 的安全升级

| 影响对象 | 没有 EIP-7951 | 有 EIP-7951 |
|---------|-------------|------------|
| **ERC-4337** | ❌ 只能使用 secp256k1，需要软件存储私钥或外部硬件钱包<br>❌ 私钥可能被恶意软件窃取<br>❌ 用户需要管理助记词 | ✅ 硬件级密钥保护：私钥存储在设备安全芯片，永不离开设备<br>✅ 生物识别验证：每次 UserOperation 都需要 Face ID / Touch ID / 指纹识别<br>✅ 批量操作和代付款场景更安全：每个操作都需要硬件签名验证 |
| **EIP-7702** | ❌ EOA 临时设置代码后，仍使用 secp256k1 签名<br>❌ 私钥存储在软件中，存在被窃取风险 | ✅ 临时代码 + 硬件签名：EOA 可以使用硬件安全芯片签名<br>✅ 生物识别保护：每次临时代码执行都需要生物识别<br>✅ 零部署风险：临时使用后恢复，结合硬件签名实现"零风险"体验 |

## 技术优势对比

| 特性 | 传统方式（secp256k1） | EIP-7951（secp256r1） |
|------|---------------------|---------------------|
| **密钥存储** | 软件存储（可导出） | 硬件安全模块（不可导出） |
| **签名方式** | 需要密码/助记词 | 生物识别（Face ID/Touch ID） |
| **用户体验** | 复杂，需要记忆 | 简单，原生体验 |
| **安全性** | 依赖用户保管 | 硬件级安全 |
| **设备支持** | 需要额外硬件钱包 | 手机原生支持 |
| **Gas 成本** | ECRECOVER (3000 gas) | P256VERIFY (6900 gas) |


```
┌─────────────────────────────────────────────────────────┐
│                   用户操作流程                            │
└─────────────────────────────────────────────────────────┘

1. 钱包初始化
   └─> 设备生成 secp256r1 密钥对
   └─> 私钥存储在安全芯片（Apple Secure Enclave / Android Keystore）
   └─> 公钥存储在链上（智能合约钱包）

2. 用户发起交易
   └─> 钱包 App 构建 UserOperation
   └─> 提示用户生物识别（Face ID / Touch ID / 指纹）

3. 设备安全芯片签名
   └─> 用户通过生物识别
   └─> 安全芯片使用私钥签名（secp256r1）
   └─> 签名返回给钱包 App

4. ERC-4337 钱包验证
   └─> 钱包的 validateUserOp 函数被调用
   └─> 调用 EIP-7951 预编译（地址 0x100）
   └─> 验证 secp256r1 签名

5. 交易执行
   └─> 验证通过，交易提交到链上
   └─> 用户完成操作
```

## 跟其他相关 EIP 的关系

- **ERC-4337**：账户抽象的应用层框架，提供智能合约钱包基础设施
- **EIP-7702**：协议层增强，允许 EOA 使用 ERC-4337 钱包代码
- **EIP-7951**：协议层预编译，原生支持 secp256r1 签名算法，**实现移动端体验革命**

三者协同工作：ERC-4337 提供框架，EIP-7702 降低门槛，EIP-7951 提供硬件安全签名能力。


**EIP-7951 的 secp256r1 支持只能在智能合约中使用**。 可以跟 EIP-7702、ERC-4337结合使用：

### 用例 1：ERC-4337 智能合约钱包

```
ERC-4337 智能合约钱包流程：
用户操作
  ↓ 使用 secp256r1 签名（设备安全芯片）
智能合约钱包的 validateUserOp
  ↓ 调用 EIP-7951 预编译（地址 0x100）验证 secp256r1 签名
EntryPoint 执行交易
```

智能合约钱包的 validateUserOp示例
```solidity
contract BiometricWallet {
    address public immutable entryPoint;
    
    // 公钥存储在链上（从设备安全芯片导出）
    uint256 public publicKeyX;
    uint256 public publicKeyY;
    
    function validateUserOp(
        UserOperation calldata userOp,
        bytes32 userOpHash,
        uint256 missingAccountFunds
    ) external returns (uint256 validationData) {
        require(msg.sender == entryPoint, "Only entryPoint");
        
        // 从 signature 中提取 secp256r1 签名
        // 这个签名是由设备安全芯片通过生物识别生成的
        (uint256 r, uint256 s) = abi.decode(
            userOp.signature, 
            (uint256, uint256)
        );
        
        // 使用 EIP-7951 预编译验证签名
        bytes memory input = abi.encodePacked(
            userOpHash,     // 32 bytes: 消息哈希
            r,              // 32 bytes: 签名 r
            s,              // 32 bytes: 签名 s
            publicKeyX,     // 32 bytes: 公钥 x
            publicKeyY      // 32 bytes: 公钥 y
        );
        
        (bool success, bytes memory result) = address(0x100).staticcall(input);
        require(success && result.length == 32, "Verification failed");
        
        uint256 verified = abi.decode(result, (uint256));
        require(verified == 1, "Invalid signature");
        
        return 0; // 验证成功
    }
}
```

### 用例 2：EIP-7702 + ERC-4337（EOA 也能用）

```
EIP-7702 + ERC-4337 流程：
1. EOA 通过 EIP-7702 交易临时设置代码（指向 ERC-4337 钱包代码）
   └─> EOA 临时"变成"智能合约钱包
2. 用户操作
   └─> 使用 secp256r1 签名（设备安全芯片）
3. 设置的代码（ERC-4337 钱包代码）的 validateUserOp
   └─> 调用 EIP-7951 预编译（地址 0x100）验证 secp256r1 签名
4. EntryPoint 执行交易
```

**关键点**：
- ✅ ERC-4337 智能合约钱包可以使用 secp256r1
- ✅ EIP-7702 让 EOA 也能使用 ERC-4337 钱包代码，从而支持 secp256r1
- ✅ 通过 EIP-7951 预编译验证签名
- ✅ 支持设备安全芯片和生物识别
- ✅ EOA 无需部署新合约，临时设置代码即可
