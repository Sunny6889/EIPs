# EIP-7951：secp256r1 曲线支持

## 1. 以太坊为什么要实现 EIP-7951

### 背景：设备安全芯片与以太坊的不兼容

我们日常使用的手机和电脑中，其实内置了专门的安全芯片。比如 iPhone 里的「安全隔区」（Secure Enclave），或者安卓手机里的 Keystore / Trust Zone / StrongBox。这块独立的物理区域通常被称为 TEE（可信执行环境）。它的特点是「只进不出」：私钥在里面生成，永远不会离开这个物理区域，外部只能请求它对数据进行签名。

这实际上就是硬件钱包的标准。而这些芯片在签名时，普遍采用了一种被 NIST（美国国家标准与技术研究院）选中的行业标准算法曲线：**secp256r1**。这也正是 WebAuthn 和 FIDO2（比如你的指纹登录、FaceID）背后的基石。

### 问题：以太坊不支持 secp256r1

尴尬的是，以太坊原生并不支持这个主流的 secp256r1。当年比特币社区出于对 NIST 曲线可能存在「国家级后门」的担忧，选择了相对冷门的 secp256k1，所以以太坊在设计账户体系时，沿用了这条曲线的传统。虽然 r1 和 k1 看起来只差一个字母，但在数学上它们完全是两种不同的语言。这就导致了一个巨大的痛点：**你手机里那个安全芯片，对着以太坊是一脸懵逼的，它无法直接签署以太坊的交易**。

以太坊显然无法强迫苹果或三星去更改芯片设计来适配 secp256k1，唯一的路就是以太坊自己去适配 secp256r1。

### 解决方案：预编译合约

用智能合约写代码去验证 r1 签名行不行？理论上行，但数学运算太复杂，跑一次验证可能要消耗几十万 Gas，这在经济上是完全不可用的。

于是，在 Fusaka 升级中，开发者祭出了大杀器：**预编译合约（Precompile）**。这相当于在以太坊虚拟机（EVM）里开了一个「后门」或「外挂」。与其让 EVM 一步步算，不如把这个验证功能直接写进客户端底层代码里。开发者只需要调用特定的地址，就能以极低的成本完成验证。

### 核心价值

**EIP-7951 原生支持 secp256r1 (P-256) 签名算法**，这意味着：

✅ **钱包可以直接调用 iPhone/Android 的安全芯片**  
✅ **支持 Passkeys（通行密钥）和 WebAuthn**  
✅ **告别助记词**：不再需要备份 12/24 个单词  
✅ **生物识别登录**：Face ID、Touch ID、指纹识别成为链上交互的原生标准

## 2. EIP-7951 具体是什么

### 技术规格

EIP-7951 在以太坊协议层添加了 `P256VERIFY` 预编译合约，用于高效验证 secp256r1 曲线上的 ECDSA 签名。

| 技术指标 | 数值/状态 |
|---------|----------|
| **预编译地址** | `0x100` |
| **Gas 成本** | 6900 gas（相比 ECRECOVER 的 3000 gas，基于实际性能基准） |
| **输入长度** | 160 字节（固定） |
| **输出长度** | 32 字节（成功）或 0 字节（失败） |
| **曲线标准** | NIST SP 800-186 / FIPS 186-5 |
| **安全级别** | 128 位（与 secp256k1 相当） |

### 预编译接口

```solidity
// 预编译地址
address constant P256_VERIFY = address(0x100);

// 验证签名（160 字节输入）
bytes memory input = abi.encodePacked(
    messageHash,  // 32 bytes: 消息哈希
    r,            // 32 bytes: 签名 r 分量
    s,            // 32 bytes: 签名 s 分量
    qx,           // 32 bytes: 公钥 x 坐标
    qy            // 32 bytes: 公钥 y 坐标
);

(bool success, bytes memory result) = P256_VERIFY.staticcall(input);
// 成功返回 0x0000...0001，失败返回空
```

### 实现原理

1. **协议层预编译支持**：在以太坊客户端底层实现 secp256r1 签名验证
2. **硬件安全模块支持**：与现代设备的安全芯片（Apple Secure Enclave、Android Keystore）兼容
3. **修复安全漏洞**：解决了 RIP-7212 中的两个关键安全漏洞（点无穷检查和模比较问题）

### 提案状态

- **状态**：Last Call（最后征集意见阶段）
- **截止日期**：2025-10-28
- **创建日期**：2025-05-27
- **预计部署**：2025 年

## 3. 有什么限制：只影响智能合约调用

### ❌ 传统 EOA 交易不支持 secp256r1

**以太坊的传统系统交易（EOA 发起的交易）仍然只能使用 secp256k1**：

```
传统 EOA 交易流程：
用户 EOA 账户
  ↓ 使用 secp256k1 签名
协议层验证（只支持 secp256k1）
  ↓
交易执行
```

**原因**：
- 以太坊协议层的交易验证硬编码了 secp256k1
- EIP-7951 只是添加了预编译合约，**只能在智能合约中调用**
- 预编译不能改变协议层的交易验证逻辑

### ✅ 任何智能合约都可以使用 secp256r1

**EIP-7951 是一个预编译合约（地址 `0x100`），任何智能合约都可以调用它来验证 secp256r1 签名**。

#### 通用使用方式

```solidity
contract AnyContract {
    // 预编译地址
    address constant P256_VERIFY = address(0x100);
    
    function verifySecp256r1Signature(
        bytes32 messageHash,
        uint256 r,
        uint256 s,
        uint256 publicKeyX,
        uint256 publicKeyY
    ) public view returns (bool) {
        // 构建输入（160 字节）
        bytes memory input = abi.encodePacked(
            messageHash,  // 32 bytes
            r,            // 32 bytes
            s,            // 32 bytes
            publicKeyX,   // 32 bytes
            publicKeyY    // 32 bytes
        );
        
        // 调用预编译验证签名
        (bool success, bytes memory result) = P256_VERIFY.staticcall(input);
        require(success && result.length == 32, "Verification failed");
        
        // 检查结果：0x0000...0001 表示验证成功
        uint256 verified = abi.decode(result, (uint256));
        return verified == 1;
    }
}
```

#### 常见应用场景

**1. ERC-4337 智能合约钱包**（最常用）
```
用户操作 → 使用 secp256r1 签名 → 钱包的 validateUserOp → 调用 EIP-7951 预编译验证
```

**2. EIP-7702 + ERC-4337**
```
EOA 临时设置代码 → 使用 secp256r1 签名 → 调用 EIP-7951 预编译验证
```

**3. 其他智能合约应用**
- 多签钱包：验证多个 secp256r1 签名
- 权限管理：使用硬件签名进行权限验证
- 游戏应用：验证玩家设备签名
- DeFi 应用：自定义签名验证逻辑

### 🔮 未来可能：EOA 交易支持 secp256r1

有一些提案（如 EIP-7932 + EIP-8030）试图让 EOA 交易也支持 secp256r1，但这些还在**草案阶段**，需要：
- 协议层修改
- 新的交易类型
- 额外的 Gas 成本

**当前状态**：
- ❌ EOA 交易：只能使用 secp256k1
- ✅ 智能合约钱包：可以使用 secp256r1（通过 EIP-7951）

优势：
- ✅ 无需密码

### 完整技术实现

#### 1. 钱包初始化（首次使用）

```typescript
// 钱包 App 初始化流程
async function initializeWallet() {
    // 1. 检查设备是否支持生物识别
    const hasBiometric = await checkBiometricSupport();
    if (!hasBiometric) {
        throw new Error('设备不支持生物识别');
    }
    
    // 2. 使用设备安全芯片生成 secp256r1 密钥对
    const keyPair = await generateSecp256r1KeyPair();
    // 私钥存储在 Apple Secure Enclave / Android Keystore
    // 私钥永不离开设备
    
    // 3. 重要：secp256r1 和 secp256k1 的地址不兼容
    // secp256k1 地址：keccak256(公钥)[12:] - 用于传统 EOA
    // secp256r1 公钥：不能用于推导传统 EOA 地址（曲线不同）
    // 
    // 在 EIP-7951 + ERC-4337 场景下：
    // - 钱包地址是智能合约地址（通过 CREATE/CREATE2 部署时确定）
    // - 公钥存储在智能合约中，用于验证签名
    // - 地址的有效性不依赖于曲线类型
    
    // 4. 使用 CREATE2 部署智能合约钱包（确定性地址）
    const salt = generateSalt(); // 随机 salt 或用户选择的 salt
    const walletAddress = await calculateCreate2Address(
        factoryAddress,
        salt,
        abi.encodePacked(entryPoint, keyPair.publicKeyX, keyPair.publicKeyY)
    );
    
    // 5. 部署智能合约钱包，将公钥存储在合约中
    // 使用 Paymaster 代付 Gas（推荐，新用户无需 ETH）
    const initCode = encodeInitCode(factoryAddress, salt, keyPair.publicKeyX, keyPair.publicKeyY);
    const deployUserOp: UserOperation = {
        sender: walletAddress,
        nonce: 0,
        initCode: initCode, // 包含部署代码
        callData: '0x',
        callGasLimit: '200000',
        verificationGasLimit: '100000',
        preVerificationGas: '50000',
        maxFeePerGas: ethers.utils.parseUnits('20', 'gwei').toString(),
        maxPriorityFeePerGas: ethers.utils.parseUnits('2', 'gwei').toString(),
        paymasterAndData: paymasterAddress, // Paymaster 代付部署 Gas
        signature: '0x' // 稍后填充
    };
    
    // 计算 Hash 并签名
    const deployHash = await entryPoint.getUserOpHash(deployUserOp);
    deployUserOp.signature = await signWithSecureEnclave(deployHash);
    
    // 发送到 Bundler
    // 实际执行流程：
    // 1. Bundler 调用 EntryPoint.handleOps()，Bundler 支付 Gas
    // 2. EntryPoint 验证签名（调用钱包的 validateUserOp，此时钱包还未部署）
    // 3. EntryPoint 执行 initCode，部署钱包合约
    // 4. Paymaster 转账给 EntryPoint 补偿 Bundler
    // 5. EntryPoint 补偿 Bundler
    const userOpHash = await sendToBundler(deployUserOp);
    await waitForUserOperation(userOpHash);
    
    console.log('钱包创建成功！');
    console.log('地址：', walletAddress);
    console.log('无需备份助记词，私钥安全存储在设备中');
}
```

#### 2. 发送交易（日常使用）

```typescript
// 发送 ETH 交易
async function sendETH(to: string, amount: string) {
    // 1. 构建 UserOperation
    const userOp = {
        sender: walletAddress,
        nonce: await getNonce(),
        callData: encodeTransfer(to, amount),
        callGasLimit: '100000',
        verificationGasLimit: '100000',
        preVerificationGas: '50000',
        maxFeePerGas: ethers.utils.parseUnits('20', 'gwei').toString(),
        maxPriorityFeePerGas: ethers.utils.parseUnits('2', 'gwei').toString(),
        paymasterAndData: paymasterAddress, // 使用 Paymaster 代付 Gas
        signature: '0x' // 稍后填充
    };
    
    // 2. 计算 UserOperation Hash
    const userOpHash = await entryPoint.getUserOpHash(userOp);
    
    // 3. 提示用户使用生物识别
    const biometricResult = await requestBiometricAuth('请使用 Face ID 确认交易');
    
    if (!biometricResult.success) {
        throw new Error('生物识别验证失败');
    }
    
    // 4. 设备安全芯片使用私钥签名（secp256r1）
    const signature = await signWithSecureEnclave(userOpHash);
    // 签名在安全芯片内部完成，私钥永不离开设备
    
    // 5. 填充签名
    userOp.signature = signature;
    
    // 6. 发送到 Bundler（实际执行流程）
    // Bundler 会：
    // a) 调用 EntryPoint.handleOps()，Bundler 支付 Gas
    // b) EntryPoint 验证签名（调用钱包的 validateUserOp）
    // c) EntryPoint 执行用户操作（调用钱包的 execute）
    // d) 如果有 Paymaster，Paymaster 转账给 EntryPoint 补偿 Bundler
    // e) EntryPoint 补偿 Bundler
    const txHash = await sendToBundler(userOp);
    
    // 7. 等待交易确认
    const receipt = await waitForTransaction(txHash);
    
    console.log('交易已提交！', txHash);
    console.log('无需输入密码，只需 Face ID 确认');
    console.log('Gas 费用：由 Paymaster 代付');
}
```

#### 3. 智能合约钱包验证（链上）

```solidity
// 智能合约钱包的验证逻辑
contract BiometricWallet {
    address public immutable entryPoint;
    uint256 public publicKeyX; // 公钥 x 坐标
    uint256 public publicKeyY; // 公钥 y 坐标
    
    function validateUserOp(
        UserOperation calldata userOp,
        bytes32 userOpHash,
        uint256 missingAccountFunds
    ) external returns (uint256 validationData) {
        require(msg.sender == entryPoint, "Only entryPoint");
        
        // 从 signature 中提取 secp256r1 签名
        // 这个签名是由设备安全芯片通过生物识别生成的
        (uint256 r, uint256 s) = abi.decode(
            userOp.signature, 
            (uint256, uint256)
        );
        
        // 使用 EIP-7951 预编译验证签名
        bytes memory input = abi.encodePacked(
            userOpHash,     // 32 bytes: 消息哈希
            r,              // 32 bytes: 签名 r
            s,              // 32 bytes: 签名 s
            publicKeyX,     // 32 bytes: 公钥 x
            publicKeyY      // 32 bytes: 公钥 y
        );
        
        // 调用 EIP-7951 预编译（地址 0x100）
        (bool success, bytes memory result) = address(0x100).staticcall(input);
        require(success && result.length == 32, "Verification failed");
        
        uint256 verified = abi.decode(result, (uint256));
        require(verified == 1, "Invalid signature");
        
        return 0; // 验证成功
    }
}
```

### 完整工作流程

```
┌─────────────────────────────────────────────────────────┐
│                   用户操作流程                            │
└─────────────────────────────────────────────────────────┘

1. 钱包初始化
   └─> 设备生成 secp256r1 密钥对
   └─> 私钥存储在安全芯片（Apple Secure Enclave / Android Keystore）
   └─> 公钥存储在链上（智能合约钱包）

2. 用户发起交易
   └─> 钱包 App 构建 UserOperation
   └─> 提示用户生物识别（Face ID / Touch ID / 指纹）

3. 设备安全芯片签名
   └─> 用户通过生物识别
   └─> 安全芯片使用私钥签名（secp256r1）
   └─> 签名返回给钱包 App

4. ERC-4337 钱包验证
   └─> 钱包的 validateUserOp 函数被调用
   └─> 调用 EIP-7951 预编译（地址 0x100）
   └─> 验证 secp256r1 签名

5. 交易执行
   └─> 验证通过，交易提交到链上
   └─> 用户完成操作
```
